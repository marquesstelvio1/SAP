# Deployment Strategy

## Purpose

The deployment baseline packages the SaaS foundation as independently runnable API, Web, and
PostgreSQL services. It exists before product features so every later module inherits the same
release, health, and rollback contract.

## Runtime Shape

| Service | Artifact | Runtime |
| --- | --- | --- |
| API | `apps/api/Dockerfile` | NestJS compiled output with `/health/live` and `/health/ready` |
| Web | `apps/web/Dockerfile` | Next.js standalone output with `/api/health` |
| Database | `compose.yaml` `postgres` service | PostgreSQL with container healthcheck |
| Backup | `saptm-database-backup` CronJob | Logical PostgreSQL backup per namespace |
| Observability | `deploy/kubernetes/observability` | OTel Collector, Prometheus, Alertmanager, Grafana |
| Resilience | HPA, PDB, topology spread | API and Web high-availability baseline |
| Resource governance | ResourceQuota, LimitRange | Namespace budgets for application and observability workloads |
| Cluster baseline | Cluster preflight and admission policies | Prerequisite controls before app rollout |

Container images are published by Container CI to GHCR. Registry naming, tags, and promotion rules
are defined in `docs/devops/container-registry.md`.

Environment promotion, Kubernetes overlays, and deployment workflow rules are defined in
`docs/devops/environment-strategy.md`. Secret requirements are defined in
`docs/devops/secrets-strategy.md` and `docs/devops/external-secrets-strategy.md`.

## Local Stack Commands

Start database only:

```bash
pnpm infra:up
```

Start full stack:

```bash
pnpm infra:stack
```

View logs:

```bash
pnpm infra:logs
```

Stop stack:

```bash
pnpm infra:down
```

## Image Build Commands

Build API image:

```bash
pnpm docker:api:build
```

Build Web image:

```bash
pnpm docker:web:build
```

## Deployment Order

1. Build API and Web images from the same commit.
2. Publish immutable `sha-<commit>` image tags.
3. Provision environment-scoped secrets.
4. Verify `saptm-runtime-secrets` and `saptm-observability-secrets`.
5. Run cluster baseline workflow if admission policies or issuers are missing.
6. Confirm latest successful database backup.
7. Apply database migrations with `pnpm db:migrate:deploy`.
8. Apply or validate observability stack.
9. Run cluster preflight.
10. Render ingress and runtime URLs from GitHub environment variables.
11. Start API instances.
12. Wait for `/health/live`, `/health/ready`, and `/metrics`.
13. Start Web instances.
14. Wait for `/api/health`.
15. Confirm Prometheus scrape and alert rules.
16. Confirm Kubernetes NetworkPolicy allows only approved ingress.
17. Confirm HPA, PDB, and pod distribution status.
18. Confirm ResourceQuota and LimitRange status for application and observability namespaces.
19. Run runtime smoke checks through `scripts/smoke-runtime.mjs`.
20. Confirm TLS certificate is issued and HTTP redirects to HTTPS.
21. Route traffic.
22. Monitor logs, metrics, traces, audit writes, and error rate.

## Production Rules

- Do not use the local Compose secret values outside local development.
- Do not run `pnpm db:migrate:dev` in production or staging.
- Do not run production migrations without a current backup.
- Do not route traffic to an instance before readiness passes.
- Use immutable image tags tied to commit SHA or release version.
- Do not deploy `latest`, branch, or pull request image tags to production.
- Do not deploy production ingress with `example.com`, localhost, or HTTP URLs.
- Do not cut over production traffic if Prometheus cannot scrape `/metrics`.
- Do not cut over production traffic if runtime smoke checks fail.
- Do not cut over production traffic if TLS is missing, expired, or not redirecting HTTP.
- Do not cut over production traffic if runtime secrets are missing or generated by an unapproved source.
- Do not cut over production traffic if API or Web pods are reachable outside approved ingress paths.
- Do not run production workloads without HPA, PDB, and readiness probes.
- Do not run production workloads without ResourceQuota and LimitRange enforcement.
- Do not deploy production workloads before cluster preflight and admission policy checks pass.
- Keep rollback images and migration rollback plan attached to every release.

## Acceptance Criteria

- API and Web have Dockerfiles.
- Compose can model PostgreSQL, API, and Web service dependencies.
- Healthchecks exist at container and application levels.
- Deployment order is documented before the first business feature.
- Staging and production Kubernetes overlays exist.
- Deployment workflow accepts immutable API and Web image tags.
- Deployment workflow renders ingress hosts from environment URL variables.
- Observability Kubernetes stack and deploy workflow exist.
- Deployment workflow runs runtime smoke checks after rollout.
- Database backup CronJob and restore runbook exist.
- Staging and production ingress overlays define TLS.
- External secret templates and runtime secret preflight exist.
- Kubernetes NetworkPolicy constrains API and Web ingress.
- API and Web have HPA, PDB, and topology spread controls.
- Application and observability namespaces have ResourceQuota and LimitRange controls.
- Cluster preflight and admission policy baseline exist.
